Functions and response curves

This is the toolbox. A response curve answers one question: given this input, how strongly should the agent care? Learn four curve shapes and one data structure and you can express almost any behaviour in the book.

The four curve families

FamilyBook formReach for it when
Lineary = m·x + bEach unit matters the same. Rare in behaviour, common as a first draft.
Polynomial (the book calls the whole family "quadratic")y = (x − c)^k + bThings that speed up or slow down: urgency that rises as health falls, damage that drops with distance.
Logistic (S-curve)y = 1 / (1 + e^−x)Soft thresholds. "Does not matter, does not matter, suddenly matters, then levels off."
Logit (sideways S)y = ln(x / (1 − x))The reverse: quick change at both ends and a flat middle. "Only the extremes are interesting."

Chapter 10 then shows how four parameters reshape any of them. These four letters come back in Part 6, because the Infinite Axis system stores every curve as exactly these.

  • m, slope: steeper or flatter, and negative to flip it.
  • k, exponent: how sharply it bends. Between 0 and 1 the bend goes the other way ("rotating the curve").
  • b, vertical shift: move the whole curve up or down.
  • c, horizontal shift: move the vertex or midpoint left or right.

Curve explorer

Input and output are both kept between 0 and 1. Pick a preset to see a behaviour, then change one parameter at a time.

How to design a curve

Do not start from a formula. Start from three sentences: what happens at input 0, what happens at input 1, and where the change is fastest. Sketch that, then pick the family that draws it. If no family fits, chapter 12's hand-made table is the answer.

The book's weapon formulas use this directly

In the big example of Part 5, every weapon's accuracy and damage is one shifted polynomial:

result = Base + Modifier − (Distance − Shift)^Exponent / Divisor

Four numbers per weapon produce a pistol that fades gently, a shotgun that falls off a cliff, and a rocket launcher that is worse up close because Shift moves the peak out to 50 feet.

Probability distributions

Chapter 11 is about populations. Not every guard has the same reaction time, and one guard does not react identically twice. A distribution describes that spread.

  • Uniform. Every value equally likely. This is plain rand(), and it looks artificial because almost nothing in life is uniform.
  • Normal (bell). Most values near the middle, few at the extremes. The book's simple recipe: add several uniform random numbers together. Three dice already give a convincing bell.
  • Triangular. A cheap approximation of the bell from just two random numbers.
  • Uneven, parabolic, Poisson. Skewed shapes for things like "usually quick, occasionally very slow".

Adding dice makes a bell

Each sample is the average of N uniform random numbers. One die is flat. Watch what a second and third one do.

Where this goes in an agent

Use it for per-agent traits rolled once at spawn (aim skill, bravery, reaction delay) and for small per-decision noise. Twenty enemies with bravery drawn from a bell around 0.5 will break and run at twenty different moments from the same code.

Response curves as data: buckets

A formula has two limits: you are stuck with shapes maths can draw, and evaluating it costs time. Chapter 12's answer is to store the curve as a table. The same structure also gives weighted random selection, which Part 5 depends on.

Picture each option as a bucket whose width is its weight. Lay the buckets end to end. Throw a ball at a random point along the row. Wider buckets catch it more often.

edge[i] = edge[i−1] + width[i]     roll = random(0, edge[last])     result = first i where roll <= edge[i]
From the book

The first bucket set models the crowd from the two-thirds game in Part 1: 5 wide for "guess 33", 3 for "guess 22", 30 for random guessers, 62 for semi-logical ones. The code is AddBucket(GUESS_33, 5); AddBucket(GUESS_22, 3); AddBucket(GUESS_RANDOM, 30); AddBucket(GUESS_SEMI, 62);

Bucket lookup

Change the widths, then throw balls. The search steps show the binary search the book uses to find the bucket quickly.

BucketWidthEdgeShareHits
Throw a ball.
// The structure from chapter 12, reduced to its core.
struct Bucket { int width; int edge; Result result; };
std::vector<Bucket> buckets;

void AddBucket(Result r, int width) {
    int prev = buckets.empty() ? 0 : buckets.back().edge;
    buckets.push_back({ width, prev + width, r });
}

Result Pick() {
    int roll = 1 + rand() % buckets.back().edge;      // 1 .. total width
    int lo = 0, hi = (int)buckets.size() - 1;
    while (lo < hi) {                                 // binary search on the edges
        int mid = (lo + hi) / 2;
        if (roll <= buckets[mid].edge) hi = mid; else lo = mid + 1;
    }
    return buckets[lo].result;
}

Four things the book builds from this one structure

  1. A function stored as a table. Evaluate an expensive curve once into an array and look values up at run time. Index by a scaled x, or binary search if x is not evenly spaced.
  2. A distribution stored as buckets. Any histogram becomes a random generator: bucket width is how often that result should occur.
  3. Hand-made curves. When no formula fits, a designer types the numbers into a file. The book stresses that this is not cheating. It is often the fastest way to the behaviour you want.
  4. Dynamic curves. Change a bucket's width while the game runs and rebuild the edges from that bucket onward. An agent that was burned by one tactic can shrink that tactic's bucket.

How many table entries are enough?

The smooth line is the formula. The stepped line is what a lookup table of that size returns. This is the book's "granularity" question from Part 4, seen early.

Check yourself
  1. You want "interest in a pickup" to be near zero until the agent is fairly close, then rise fast, then level off. Which family? (Logistic, with the slope negative on distance or the input inverted.)
  2. Three options have weights 6, 3 and 1. What are the edges, and how often is the second picked? (6, 9, 10. Thirty percent of the time.)
  3. Why store bucket edges as cumulative sums instead of widths? (So one random number and one search find the result, without summing every time.)
