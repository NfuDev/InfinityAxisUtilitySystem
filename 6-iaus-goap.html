From the book to an Infinite Axis Utility System, and into GOAP

This page connects the book's tools to the system you want to build. It is my synthesis, not a summary of the book.

Where this material comes from

The book (2009) never uses the name "Infinite Axis Utility System". Dave Mark described IAUS later, mainly in his GDC AI Summit talks "Architecture Tricks: Managing Behaviors in Time, Space, and Depth" (2013) and "Building a Better Centaur: AI at Massive Scale" (2015, with Mike Lewis). What follows is my understanding of those talks plus common practice. The GOAP integration patterns are standard approaches, not something either source prescribes. Treat the numbers in the widgets as starting points to tune.

Why multiply, and the compensation factor

Multiplying gives every consideration a veto: no ammo means the Shoot decision scores zero regardless of how good the target is. The cost is that products of fractions shrink. Three axes at 0.9 give 0.73. Six give 0.53. A decision with more axes would lose to a simpler one purely for being more carefully described.

Mark's fix is a compensation step that pulls each axis score up by an amount that depends on how many axes the decision has:

float Compensate(float score, int axisCount) {
    float modification = 1.0f - (1.0f / axisCount);
    float makeUp       = (1.0f - score) * modification;
    return score + makeUp * score;          // still 0 when score is 0, still 1 when score is 1
}

float ScoreDecision(const Decision& d, const Context& ctx, float bestSoFar) {
    float total = d.weight;
    for (const Consideration& c : d.considerations) {
        float raw  = c.input(ctx);                                   // e.g. distance in metres
        float x    = clamp((raw - c.min) / (c.max - c.min), 0, 1);   // bookends
        float axis = clamp(EvaluateCurve(c.curve, x), 0, 1);         // m, k, b, c
        total *= Compensate(axis, d.considerations.size());
        if (total <= bestSoFar) return 0;                            // cannot win: stop early
    }
    return total;
}

Multiplication and compensation

Set how many axes the decision has and what each one scores. Then drag any single axis to zero.

Authoring rules that keep this tunable
  • One consideration, one question. "Am I healthy enough?" and "Is the target close enough?" are separate axes even if they use the same curve.
  • Weights rank categories, not preferences. Use a handful of bands (for example idle 1, normal combat 2, urgent 3, emergency 5). Let considerations do the fine work inside a band. This avoids the book's climbing fader syndrome.
  • Put the cheapest and most likely-zero axis first. "Has ammo" before "line of sight raycast", so the early-out skips the expensive one.
  • Build a debug view first. For any agent, show every decision's final score and each axis value. This is compartmentalised confidence made practical: when a result looks wrong you can see which single axis caused it.

Contexts: scoring per target

The Shoot decision above assumes one enemy. In practice you score it once for every visible enemy, exactly as the book scored every (Dude, weapon) pair. The option that wins is "Shoot at Evil Genius", and the target comes along with it into whatever executes the action.

for (Decision& d : agent.decisions)
    for (Context& ctx : d.MakeContexts(agent))      // one per target, per cover point, ...
        options.push_back({ &d, ctx, ScoreDecision(d, ctx, 0) });

Option chosen = WeightedRandom(options);            // or highest, during early development

Combining it with GOAP

GOAP and utility answer different questions. GOAP answers how: given a goal, search for a sequence of actions whose effects satisfy it. Utility answers what matters now. Classic GOAP is weak exactly where utility is strong: goals usually have fixed priorities and action costs are constants. There are three places to plug the scorer in, and they can be used together.

PatternWhat utility decidesWhat GOAP decidesUse when
A. Utility picks the goalWhich goal to pursue. Each goal is an IAUS decision.The action sequence that reaches it.Almost always. This is the cleanest split and the first one to build.
B. Utility prices the actionsEach action's cost, recomputed from its utility at plan time.The cheapest plan, which now reflects the situation.The planner keeps choosing a technically valid but silly route.
C. Utility binds the parametersWhich target, which cover point, which weapon an action uses.Sequence only. Actions arrive with their best target already chosen.Many targets or positions. Keeps the planner's search space small.

Pattern B in one line

cost = baseCost × (1 + k × (1 − utility))     utility in 0..1, k around 1 to 3

A high-utility action costs its base price. A low-utility one costs up to (1 + k) times more. Costs stay positive, which A* requires, and they never drop below the base cost, so a heuristic built from base costs stays valid.

Utility-driven GOAP, patterns A and B together

This uses the same world sliders as the widget above. Three goals are scored as IAUS decisions. The winning goal goes to a real, tiny planner (uniform-cost search over six actions). Shoot and Melee are priced from their action scores above.

Things to try: empty the magazine at long range (the plan becomes Reload then Shoot). Then bring the enemy to 2 m with an empty magazine (Melee becomes the whole plan, because its utility is high and Reload plus Shoot is now the expensive route). Drop health to 0.2 and the goal itself changes.

One detail worth copying: when Shoot is priced for the planner, its Ammo axis is left out. In the pure scorer above, "no ammo" has to zero the action because nothing else will. In GOAP, ammo is a precondition and the planner fixes it by inserting Reload, so pricing it a second time would wrongly make Reload-then-Shoot look terrible.

The control loop

// Runs on a timer (for example every 200-300 ms, staggered across agents) and on events.
void Agent::Think() {
    // 1. PATTERN A: score every goal as an IAUS decision.
    Goal* best = nullptr; float bestScore = 0;
    for (Goal& g : goals) {
        float s = ScoreDecision(g.decision, MakeContext(g), 0);
        if (&g == currentGoal) s *= (1 + inertia);            // decision momentum (Part 5)
        if (s > bestScore) { bestScore = s; best = &g; }
    }

    // 2. Keep the current plan if the goal did not change and the plan is still valid.
    if (best == currentGoal && plan.IsStillValid(world)) return;   // "can I still do this?"

    // 3. PATTERN C: bind parameters before planning.
    for (Action& a : actions) a.target = BestContextFor(a);         // highest-scoring target

    // 4. PATTERN B: price actions from utility, then plan.
    for (Action& a : actions)
        a.cost = a.baseCost * (1 + k * (1 - ScoreDecision(a.decision, a.target, 0)));

    currentGoal = best;
    plan = planner.Plan(world.State(), best->desiredState, actions);
    if (plan.empty()) MarkGoalFailed(best);                         // scores lower for a while
}
Pitfalls specific to this combination
  • Replanning storms. If goal scores are close, the agent replans every tick. Use inertia on the current goal, and only replan when the goal changes or the plan becomes invalid. This is the strobing problem from Part 5 with a more expensive symptom.
  • Commit at action boundaries. Like the book's "rescore after each shot", prefer to switch goals between plan steps. Reserve mid-action interrupts for a small set of urgent events.
  • Unreachable goals. A goal can score highest and have no plan. Record the failure and suppress that goal's score for a few seconds, or it will be chosen and fail forever.
  • Stale costs. Utility-based costs are a snapshot. A long plan was priced with numbers that will be wrong by step four. Keep plans short and revalidate, which is the book's information-expiry point.
  • Do not put precondition logic in curves. "Needs ammo" belongs in the GOAP precondition, where the planner can solve it by inserting Reload. A curve that zeroes the action just hides it. Use curves for preference, preconditions for possibility.
  • Keep the planner's state boolean and the utility's inputs continuous. They are different views of the same world. Derive both from one world-state object so they cannot disagree.

A build order that works

  1. Curve evaluator. Four types, four parameters, clamped output. Test it with a plotter like the one in Part 3.
  2. Inputs. A registry of named functions that read one number from the agent's world state.
  3. Consideration and Decision as data. Data assets or tables, not code.
  4. Scorer with compensation and early-out.
  5. Debug view. Per agent: every decision, every axis, raw input, normalised input, curve output.
  6. Pattern A. Replace your GOAP goal priorities with scored goals. Add inertia. Ship this before anything else.
  7. Contexts for target selection (pattern C).
  8. Pattern B only where plans look wrong.
  9. Weighted random selection last, once the scores are trustworthy, so that variation is not hiding bugs.
Check yourself
  1. A decision has five axes all scoring 0.8. What is the raw product, and why is that a problem? (0.33. It would lose to a one-axis decision scoring 0.5 despite being a better fit on every axis.)
  2. Where should "the agent needs a key to open this door" live: a consideration or a precondition? (A precondition, so the planner can add "get key" to the plan.)
  3. Which pattern gives the most benefit for the least work in an existing GOAP system? (Pattern A: score the goals.)
